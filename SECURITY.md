# InsightX Security Architecture & Threat Model

**Document**: SECURITY.md  
**Classification**: Production Security Specification  
**System**: InsightX — AI-Powered Business Intelligence & Customer Analytics Platform  

---

## 1. Security Philosophy & Defense-in-Depth

The InsightX architecture assumes that **LLMs are untrusted query generators**. Even when instructed to produce safe SQL, model outputs may be vulnerable to prompt injection, hallucinated syntax, or adversarial manipulation. 

To ensure complete safety, InsightX enforces a five-tier **Defense-in-Depth** model:

```
User Query
   │
   ▼
[ Tier 1: Input Sanitization & Intent Planner ]
   │
   ▼
[ Tier 2: AST & Lexical SQL Safety Validator ]
   │ (Rejects DDL/DML, multi-statements, table violations)
   ▼
[ Tier 3: Read-Only Database Role Enforcement ]
   │ (PostgreSQL insightx_readonly / SQLite mode=ro)
   ▼
[ Tier 4: Execution Sandbox & Resource Capping ]
   │ (Statement timeout 10s, LIMIT 500 rows enforced)
   ▼
[ Tier 5: Output Sanitization & Formula Neutralization ]
   │ (CSV export escaping, HTML entity encoding)
   ▼
Frontend Render (Text-only, no eval / dangerous HTML)
```

---

## 2. Tier 1: Input Sanitization & Intent Planning

- **No System Catalog Leaks**: The system prompt and query planner expose only approved analytics schemas (`fact_sales`, `dim_customer`, `dim_product`, `dim_date`, `dim_country`, `customer_rfm`).
- **Prompt Injection Resilience**: The database contents (e.g., product descriptions, country names) are treated as passive data. Instructions embedded within text fields are never executed as system instructions.
- **Credential Segregation**: Database connection strings, API keys, and server environment variables are never embedded in prompts or returned in API responses.

---

## 3. Tier 2: AST & Lexical SQL Validator

Every query generated by an LLM or user must pass the `validateAndSanitizeSql` engine before reaching the database:

1. **Strict Read-Only Grammar**:
   - The query must begin with `SELECT` or a read-only Common Table Expression (`WITH ... SELECT`).
   - Any query containing mutation keywords (`INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `CREATE`, `TRUNCATE`, `REPLACE`, `ATTACH`, `DETACH`, `PRAGMA`, `VACUUM`, `EXEC`, `EXECUTE`, `GRANT`, `REVOKE`, `COPY`, `MERGE`, `UPSERT`) is aborted with a `Security Error`.
2. **Multi-Statement Prevention**:
   - Queries containing internal semicolons (`;`) outside of quoted literals are rejected immediately to prevent stacked query injection (e.g., `SELECT 1; DROP TABLE ...;`).
3. **Table Whitelist Enforcement**:
   - The engine parses `FROM` and `JOIN` clauses. Only explicitly approved tables or query-scoped CTEs are permitted.
   - Attempts to access `sqlite_master`, `pg_catalog`, `information_schema`, or internal system tables are blocked.
4. **Enforced Row Capping**:
   - If a query lacks a `LIMIT` clause, `LIMIT 500` is automatically appended.
   - If a user specifies an unbounded or excessive limit (`> 500`), it is clamped to 500.

---

## 4. Tier 3: Database Role Isolation

Even if a malicious query were to bypass application-level validation, the database engine enforces physical write denial:

- **PostgreSQL**:
  Queries run under the `insightx_readonly` role created in `backend/db/read_only_role.sql`. The role has:
  ```sql
  REVOKE ALL ON ALL TABLES IN SCHEMA public FROM insightx_readonly;
  GRANT USAGE ON SCHEMA public TO insightx_readonly;
  GRANT SELECT ON TABLE fact_sales, dim_date, dim_customer, dim_product, dim_country, customer_rfm TO insightx_readonly;
  ALTER ROLE insightx_readonly SET statement_timeout = '10000';
  ```
- **SQLite**:
  The connection string is initialized in strict read-only mode (`open: true, readOnly: true` in `node:sqlite` and `mode=ro` URI in Python). Any attempt to write causes the engine to throw an I/O permission error.

---

## 5. Tier 4: Resource Capping & DoS Prevention

- **Statement Timeouts**: All analytical queries are subject to a maximum 10-second execution deadline (`SQL_TIMEOUT_SECONDS=10`).
- **Memory Protection**: Maximum JSON payload limit is restricted to 1 MB. Large result sets are truncated to 500 rows.
- **Connection Pooling**: Database handles are pooled and closed gracefully.

---

## 6. Tier 5: Output Sanitization & CSV Formula Neutralization

Spreadsheet software (Microsoft Excel, Google Sheets, LibreOffice) can execute arbitrary formulas if cells begin with `= `, `+`, `-`, or `@` (known as CSV Formula Injection / CSV Injection).

InsightX neutralizes this vector in `server.ts` and `CopilotView.tsx`:
```typescript
const sanitizeValue = (val: any): string => {
  if (val === null || val === undefined) return '';
  let str = String(val);
  if (/^[=+\-@\t\r]/.test(str)) {
    str = "'" + str; // Neutralize formula execution by prefixing single-quote
  }
  return str;
};
```

---

## 7. Frontend XSS Prevention

- All SQL text and model explanations are rendered using React's virtual DOM text nodes, never using `dangerouslySetInnerHTML`.
- Chart inputs are strongly typed against returned numeric arrays.

---

## 8. Verification & Test Coverage

Security controls are verified by automated unit tests in `tests/test_sql_security.py`:
- `test_valid_select_queries_accepted`: Verifies standard analytics.
- `test_mutation_keywords_rejected`: Verifies rejection of DROP/DELETE/INSERT/ALTER.
- `test_multi_statement_injection_rejected`: Verifies rejection of stacked queries.
- `test_disallowed_tables_rejected`: Verifies rejection of system catalogs.
- `test_limit_enforcement`: Verifies row capping at 500 rows.
